# AgentOS 数据库数据完整性协议 v1.0

> 用户 2026-10-23 裁决（**系统级硬要求，学术态度问题**）：
> **「我们所有的数据库数据，一定要确保是 100% 准确，没有任何臆测的数据，不可以有任何可信度缺口……
> 务必做到 100%，这是学术态度的问题。我们要杜绝 garbage in garbage out 这种状况。」**
>
> 本协议把这句话变成**可机械执行、可阻断交付**的门禁。非建议、非可选。
> 与 `DELIVERABLE-STANDARD.md` 并列执行，优先级相同（对应 R6）。

---

## 0. 一句话定义

**数据库的 100% 准确 ≠ 模型知道得多。**

> 100% 准确 = **每个非空格都能被第三方仅凭表内给出的定位，独立复核出同一个结论。**

| | 允许 | 禁止 |
|---|---|---|
| 主表数值 | 「Rm 370~500（GB/T 700-2006 表 3，热轧，厚度≤16mm）」 | 「Rm 约 400（手册典型值）」 |
| 取不到证据 | 空 + 等级 C + 复核状态「不可得·已定论」 | 填一个看起来合理的数 |
| 源冲突 | 标 `conflicted` + 裁决口径 + 采用值 + 冲突记录 | 静默取其中一个 |
| 尺寸分档 | 写明所取分档（厚度/直径/壁厚） | 跨分档套用 |

**判别口**：把这张表交给一个完全没参与编制的人，他能不能**仅凭表内定位**独立复核出同一批数？
不能的格，就是不合格格。

**推论（本协议的硬核）**：模型先验（记忆、手册印象、"典型值"）**不是来源**。
它既不能落进主表，也不能给主表提供数字 —— 这与 `TRUTH-AND-EVIDENCE.md` §3 规则 2
「model / none / user 来源永远不能产生 verified 机器事实」完全一致。

## 1. 单元级证据状态（沿用 `TRUTH-AND-EVIDENCE.md` §2 词表）

| 状态 | 数据库落地形态 | 能否进主表 |
|---|---|---|
| verified（E1+） | 定位到具体标准条款/厂家技术条件版本 + 快照 + 适用条件 | ✅ |
| derived（E2/E3） | 由已验证数据换算（单位换算、厚度分档取值、插值） | ✅ 但必须标 `derived` + 推导链 |
| observed（E1） | 厂家技术条件/公开数据表原文数值（非标准原文） | ✅ 标 `observed` + 来源 |
| assumption / **E0** | 模型先验、手册印象、常见值、记忆 | ❌ **禁止进主表** |
| unknown | 无证据 | ❌ 只能落在「待核 / 不可得」区 |
| conflicted | 两源冲突 | ❌ 必须先裁决再入库 |

**铁律 D-0：E0 不得进主表。** 允许它出现在「待核清单」里作为待办，
但那不是数据，那是待办 —— 两者不可混淆。

### 1.5 参数库 / 材料库：主键必须落到「厂商 × 牌号」

用户 2026-10-23 追加裁决：**「作为最为基础的数据库，我希望我们的数据就是 by 牌号、厂商，
确保数据能够与官方数据相符。」**

对参数库、材料库、选型库这类**可被工程决策直接引用**的数据库，通用牌号 + 手册典型值的组织方式
**不合格**。主键必须是：

```
厂商 + 厂商牌号 + 产品形态 + 规格范围 + 交货状态
```

| 纪律 | 内容 |
|---|---|
| **V-1** | 一行 = 一家厂的一个牌号的一种形态/规格/状态；同牌号跨厂、跨形态、跨状态**必须分行** |
| **V-2** | 成分与力学的一级权威源 = **该厂商的官方产品手册 / 技术条件 / 产品数据表**（最新版，标版本与日期）；国标/国际标准为次级源，且以厂商文件为准 |
| **V-3** | 厂商文件未述的字段，写「厂商文件未述」或留空并入附表 B；**禁止自撰补齐**（"厂商文件未述"本身就是合格答案） |
| **V-4** | 物理性能（密度/熔点/电导率/膨胀系数…）厂商数据表通常不含 → 另取权威源并在**独立来源列**标注；无法绑定权威源则走 C3 边界定论 |
| **V-5** | "与官方数据相符"的判据 = 第三方拿厂商文件逐条对照能复现本行每一个数值；凡本行数值在厂商文件中查不到对应项，即为不合格 |
| **V-6** | 数值列一律以**纯文本**落表（防 `08→8`、`12%→0.12`、日期自动转换等静默数据类型损坏） |

**反面（已实证）**：以"通用牌号 + 模型先验典型值"建库，164 行中 23.9% 的字段含
"典型/约/≈/估计"类措辞，**严格口径下 0 行可溯源** —— 整库报废。
这正是本协议要阻断的 garbage in。

## 2. 溯源粒度规范（定位必须能被"点开"）

每个填了值的字段必须同时具备**三件套**：

1. **来源实体** —— 标准号 + 版本年 + 条款/表号
   （例：`GB/T 700-2006 表 3`），或厂家技术条件编号 + 版本 + 页/表
2. **锚点** —— 条款号 / 表行 / 页码，或 URL + **本地快照文件路径**
3. **适用条件** —— 交货状态 + 规格分档（厚度/直径/壁厚）+ 温度区间（若适用）

**不接受的定位写法**（一律判 D-2 FAIL）：
`手册典型值`、`资料`、`网络资料`、`常见值`、`约`、`大概`、`经验值`、`估计值`、`参考值`、`行业普遍`。

---

## 3. 数据库版三条闭合路径（沿用 `ZERO-GAP-STANDARD.md` §2）

| 路径 | 数据库落地 | 落点 |
|---|---|---|
| **C1 查证补齐** | 取到权威来源 | 主表 + 定位三件套 |
| **C2 替代口径定论** | 原始不可得，但可由已验证数据推导 | **分区隔离**：独立「推导值」列或附表 A + 置信度（高/中/低，按 ZERO-GAP §3.2）+ 推导链（前提→方法→结果→失效条件） |
| **C3 边界定论** | 确认不可得 | 该格**留空** + 等级 `C` + 复核状态「不可得·已定论」+ **三要素**（查证路径 + 影响评估 + 本报告判断），进附表 B |

**铁律**：C3 的"格位留空"是**结论性留空**（已定论），不是 K1 缺口 —— 附表 B 里必须写死判断。
两者在机械门禁中用「复核状态」列区分，**不靠空格区分**。

---

## 4. 冲突裁决规则

同一字段、同一牌号、同一条件下出现不同取值时：

1. **优先级**：现行国家标准 > 厂家技术条件（该牌号专用）> 权威手册 > 教材/百科/网页二手
2. **同级**：取版本较新者
3. **仍冲突**：取**工程保守值**（偏安全侧），标 `conflicted`，写入附表 B 冲突清单，
   记录两源、差异量级、采用理由、影响评估
4. **禁止**：静默取一个；禁止用"取中间值"回避裁决

---

## 5. 数据库必备列结构

业务列之外，任何数据库表必须带这 4 列（列名可按现场习惯改，语义不得缺）：

| 必备列 | 内容 | 机器判据 |
|---|---|---|
| `证据等级` | E0 / E1 / E2 / E3 / E4 或 verified / derived / observed / unknown / conflicted | 主表内不得出现 E0 |
| `来源定位` | 标准号+条款/表，或 厂家技术条件+版本+页/URL + 快照路径 | 不得为空；不得含 §2 禁用措辞 |
| `复核状态` | 已核验 / 待核 / 不可得·已定论 / 冲突待裁 | 非「已核验」的格不得留在主表 |
| `复核依据` | 快照文件路径 + SHA256（+ 抓取时间） | 文件必须存在且哈希匹配 |

## 6. 机械门禁（绝对硬门禁，无豁免）

脚本：`skills/professional-report-deliverable/scripts/data_integrity_gate.py`

| 编号 | 检查 | 判定 |
|---|---|---|
| **D1** | 主表存在 `E0` / `assumption` / `模型先验` 的行或格 | FAIL |
| **D2** | 有值的格，其 `来源定位` 为空或含 §2 禁用措辞 | FAIL |
| **D3** | 有值的格，其定位缺适用条件（无交货状态 / 无规格分档） | FAIL |
| **D4** | `复核状态` ≠「已核验」的格仍挂在主表 | FAIL |
| **D5** | 同一（牌号, 字段, 条件）出现多个不同取值且未标 `conflicted` | FAIL |
| **D6** | `复核依据` 指向的快照文件缺失，或 SHA256 不匹配 | FAIL |
| **D7** | 必填格为空 / 整行空 / 列名缺失 | FAIL |
| **D8** | 主表行数与来源清单声明的规模不符 | FAIL |

**门禁纪律**（沿用 ZERO-GAP §5.3）：
门禁红时**禁止**改脚本、放宽关键词、删检查项来"让它变绿"；
输出必须是**可审阅清单**（逐条给出：文件 / 行 / 列 / 格 / 命中片段 / 缺什么），不是二值 PASS/FAIL。

## 7. 抽样复核（不可省）

| 范围 | 比例 | 要求 |
|---|---|---|
| 数值列 | 100% | 脚本比对定位与快照 |
| 文本列 | ≥10% 且 ≥20 格 | 人工盲复核 |
| 每个来源族 | ≥2 个牌号 | 独立复核人盲审（只看定位，不看结论） |
| 冲突项 | 100% | 必须经裁决并入附表 B |

**盲审纪律**：复核人不得是数据生产者本人；盲审只允许沿着"来源定位"去找源，
不得用"我记得应该是"来判定。

## 8. 交付形态

| 交付件 | 内容 |
|---|---|
| 主表 | 全部格为 verified / derived / observed，`复核状态` 全为「已核验」 |
| 附表 A | C2 推导值（分区隔离 + 置信度 + 推导链） |
| 附表 B | C3 不可得清单与冲突清单（三要素 + 裁决记录） |
| 附表 C | 来源快照清单（路径 + SHA256 + 抓取时间 + 许可说明） |
| 门禁报告 | `data_integrity_qa.json`（脚本输出，附于交付） |

**禁止**：用"待补充"备注、`—`、灰色字体、隐藏列等方式在主表里夹带未核验值。

## 9. 与既有协议的关系

- 本协议是 **R6**：R3（数据 100% 可推敲）+ R5（零缺口）在**数据库 / 参数表 / 材料库**上的落地细则。
- 真值词表沿用 `TRUTH-AND-EVIDENCE.md` §2；闭合路径沿用 `ZERO-GAP-STANDARD.md` §2；
  门禁纪律沿用 `ZERO-GAP-STANDARD.md` §5.3。
- 与 `QUALITY-GATE.md` 并列执行，不互相替代：质量门禁管"做得对不对"，
  数据完整性门禁管"这些数**凭什么**"。
- 报告类交付仍受 R1–R5 全套约束；本协议只增加数据库维度的额外要求。
